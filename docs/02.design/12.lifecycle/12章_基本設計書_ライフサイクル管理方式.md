## 12.1. 設計方針

- **版を管理するものはすべて自動で追従する**: 個人開発のため、脆弱性の通知を待って手動で対応する方式は採らない
- **パッチとマイナーは自動、メジャーは手動**: メジャーバージョンの更新は人が判断して適用する。
  Kubernetes はマイナーバージョンの更新も手動とする。ダウングレードできず、API の削除を伴いうるためである
- **コードと差分が出ない更新はサーバ上で行う**: コードで版を指定していないものは、サーバ上で毎日自動更新する
- **コードの版指定は更新の上限に限る**: コードには手動で更新する単位（メジャーバージョン等）だけを指定し、
  その範囲内の版は指定しない。範囲内の更新を自動で取り込めるようにするためである
- **版は再現性の対象外とする**: 再構築では、指定の範囲内でその時点の版を導入する
- **停止を伴う更新は早朝に行う**: 単一インスタンス構成のため、更新と再起動は時間帯と順序を固定する

## 12.2. 対象ごとの更新方式

| 対象 | コードで指定する範囲 | 自動の更新 | 手動の更新 |
| ---- | -------------------- | ---------- | ---------- |
| OS パッケージ（コンテナランタイム、MySQL、Docker のパッケージを含む） | OS の LTS 版 | サーバ上で毎日、配布元の更新をすべて適用する（[12.3](#123-os-パッケージの更新と再起動)） | LTS 版の移行 |
| Kubernetes | マイナーバージョン | サーバ上で毎日、パッチを適用する（[12.4.3](#1243-パッチバージョンの自動更新)） | マイナーバージョン（[12.4.1](#1241-マイナーバージョンの適用方式)） |
| Flannel / External Secrets Operator / local-path-provisioner / metrics-server | メジャーバージョン | サーバ上で毎日、マイナーとパッチを適用する（[12.7](#127-アドオンと-oci-cli-の自動更新)） | メジャーバージョン |
| cert-manager | メジャーバージョン | 同上。<mark>`1.14` 系からの段階的な更新が完了するまで自動更新の対象外（[Issue #174](https://github.com/Seiya-Nakagawa/infra-oci/issues/174)）</mark> | メジャーバージョン |
| ingress-nginx | 版を固定する | 開発が終了しているため行わない | 別製品への移行（<mark>[Issue #161](https://github.com/Seiya-Nakagawa/infra-oci/issues/161)</mark>） |
| OCI CLI（サーバ） | メジャーバージョン | サーバ上で毎日適用する（[12.7](#127-アドオンと-oci-cli-の自動更新)） | メジャーバージョン |
| CI の実行ツール（ansible-core、Ansible コレクション、Python、OCI CLI） | メジャーバージョン | CI の実行時に、範囲内の最新版を取得する | メジャーバージョン |
| Terraform 本体と Provider | メジャーバージョン | CI の実行時に、範囲内の最新版を取得する | メジャーバージョン |
| GitHub Actions | メジャーバージョン（版の指定が必須） | 同じメジャーバージョン内の更新は自動で反映される | メジャーバージョン |

自動更新の方針は [6章 6.6節](../06.security/6章_基本設計書_セキュリティ設計.md#66-os-堅牢化脆弱性対策) で扱う。

### 12.2.1. 日次の実行順序

サーバ上の日次処理は、次の順に実行する（日本時間）。停止中で実行できなかった回は、後から実行しない。

| 開始時刻 | 処理 |
| -------- | ---- |
| 03:00 | データベースのバックアップ |
| 03:30 | OS パッケージの更新 |
| 04:00 | Kubernetes のパッチ更新 |
| 04:30 | アドオンと OCI CLI の更新 |
| 05:00 | 再起動（必要な場合のみ） |

この順序と競合しないように、03:00 から 05:30 の間は本番への適用（main へのマージ）を行わない。

## 12.3. OS パッケージの更新と再起動

| 項目 | 方針 |
| ---- | ---- |
| 適用範囲 | ディストリビューションの標準更新とセキュリティ更新、追加した Docker のリポジトリ。バックポートは対象外 |
| 版の上限 | OS パッケージは配布元の提供版に追従する。Docker のリポジトリはメジャーバージョンを含めて追従する |
| パッケージの固定 | Kubernetes のパッケージは固定し、OS の自動更新の対象から外す（[12.4.3](#1243-パッチバージョンの自動更新) で更新する） |
| 自動再起動 | 再起動が必要な場合のみ、05:00 に自動で再起動する |
| 自動再起動の前提 | 手動で 1 回再起動し、全サービスが復帰することを確認してから有効にする |
| 再起動後の確認 | ノードが Ready、全 Pod が稼働または完了、データベースが稼働していることを確認し、満たさない場合は通知する |
| 失敗時 | 更新の失敗を通知する（[9章 9.4節](../09.monitoring/9章_基本設計書_監視・ログ設計.md#94-通知方式)） |

設定値は [OS詳細設計書](../../03.detailed-design/OS詳細設計書.md) で扱う。

## 12.4. Kubernetes のバージョン管理

- クラスターのコンポーネントはパッケージのバージョンを固定し、意図しない更新を防ぐ
- マイナーバージョンを上げる場合は、コードの指定を変更してから適用する
- パッチバージョンは、コードを変更せずにサーバ上で自動更新する
- シングルノード構成のため、更新中はサービスが停止する。
  無停止での更新は行わない
- マイナーバージョンを上げる前に、アドオンがそのバージョンに対応することを確認する

### 12.4.1. マイナーバージョンの適用方式

`k8s_version`（マイナーバージョン）の変更だけでは APT リポジトリが切り替わるのみで、
パッケージは固定（`hold`）されているため、クラスターは更新されない。
そのため、Ansible の `kubernetes` ロールに、クラスターを指定のマイナーバージョンへ
更新する処理を設ける。

| 項目 | 方針 |
| ---- | ---- |
| 起動条件 | 稼働中のクラスターのバージョンが `k8s_version` より低い場合のみ実行する。一致していれば何もしない（冪等） |
| 更新の単位 | kubeadm の制約により、マイナーバージョンは 1 つずつしか上げられない。差が 2 以上ある場合は更新せずに失敗させる |
| パッチバージョン | 指定のマイナーバージョンの最新パッチ（`<k8s_version>.*`）を APT から取得して適用する |
| 実行環境 | 本番は CI/CD（main マージ）のみ。`--check` では更新処理を実行せず、実適用でのみ検証される |

更新処理の流れは次のとおり。

1. APT リポジトリと署名鍵を `k8s_version` に切り替える（鍵は版ごとに取得し直す）
2. `kubeadm` の固定を外し、対象バージョンへ更新する
3. `kubeadm upgrade plan` で更新可能であることを確認する
4. `kubeadm upgrade apply` でコントロールプレーンを更新する
5. ノードを drain し、`kubelet`・`kubectl` を更新して `kubelet` を再起動し、uncordon する
6. 3 パッケージを再度固定し、API Server が正常（`/readyz`）になるまで待機する

### 12.4.2. 段階的な更新の運用

シングルノードのため更新中は全サービスが停止し、ダウングレードもできない。
そのため、複数のマイナーバージョンを一度に上げず、**1 段階ごとに PR・CD・動作確認を行う**。

| 項目 | 方針 |
| ---- | ---- |
| 進め方 | `k8s_version` を 1 つ上げる PR を作成し、CD の完了と動作確認を終えてから次の段階へ進む |
| 事前確認 | 更新前に、使用中の非推奨 API の有無と、アドオンの対応バージョンを確認する。直前の DB バックアップが成功していることも確認する |
| 動作確認 | ノードが Ready、全 Pod が Running、各サービスの HTTPS 疎通、Portfolio の死活監視が正常であることを確認する |
| 失敗時 | 次の段階へ進まず原因を調査する。`kubeadm upgrade apply` は更新前の etcd とマニフェストをバックアップするため、復旧の起点とする |
| アドオン | 稼働中の版が更新後の Kubernetes に対応することを、更新の前に確認する。ingress-nginx は各段階で動作のみ確認する |

### 12.4.3. パッチバージョンの自動更新

稼働中のマイナーバージョン内の最新パッチへ、サーバ上の定期実行（systemd タイマー）で更新する。
スクリプトと systemd の定義は本リポジトリで管理し、Ansible の `kubernetes` ロールが CD で配置する。
サーバ上では直接編集しない。

| 項目 | 方針 |
| ---- | ---- |
| 実行時刻 | 毎日 04:00。データベースの日次バックアップの後に実行する。停止中で実行できなかった回は、後から実行しない |
| 起動条件 | コントロールプレーンまたは `kubelet` より新しいパッチがある場合のみ更新する。なければ何も変更せず、サービスも停止しない |
| 更新の範囲 | 稼働中のマイナーバージョン内に限る。APT リポジトリに同じマイナーバージョンの版がない場合は何もしない。コントロールプレーンと `kubelet` のマイナーバージョンが異なる場合は失敗とする |
| 公開後の待機 | 設けない。公開されたパッチは次の実行で適用する |
| 中止条件 | 当日のバックアップが成功していない、またはノードが Ready でない場合は、更新を開始せず失敗として扱う |
| 排他 | マイナーバージョンの更新（CD）と同時に実行しない |
| 失敗時 | 固定の再設定と uncordon を行い、失敗を通知する（[9章 9.4節](../09.monitoring/9章_基本設計書_監視・ログ設計.md#94-通知方式)）。自動の切り戻しは行わない |
| 失敗後の再実行 | 停止の繰り返しを防ぐため、更新を開始した後に失敗した場合は記録を残し、記録がある間は更新しない。原因に対処して記録を削除すると再開する。開始前の中止は記録を残さず、次の実行で再び判定する |
| 内容確認 | 変更せずに更新の有無と中止条件の判定結果を表示する実行方法を設ける |

更新処理の流れは次のとおり。

1. 中止条件と、新しいパッチの有無を確認する
2. `kubeadm` の固定を外して対象の版へ更新し、`kubeadm upgrade plan` で更新可能であることを確認する
3. `kubeadm upgrade apply` でコントロールプレーンを更新する
4. ノードを drain し、`kubelet`・`kubectl` を更新して `kubelet` を再起動し、uncordon する
5. 3 パッケージを再度固定し、API Server が正常（`/readyz`）でノードが Ready になることを確認する

途中で失敗した状態から再実行した場合は、コントロールプレーンと `kubelet` の版を別々に判定し、
未完了の工程から更新する。

## 12.5. 証明書のライフサイクル

| 項目 | 方針 |
| ---- | ---- |
| 発行 | cert-manager が Let's Encrypt から自動取得する |
| 更新 | 期限前に自動更新する。手動での更新作業は行わない |
| 失効時の影響 | HTTPS での接続が不可となるため、更新の失敗はサービス影響として扱う |

## 12.6. EOL への対応

| 対象 | 対応 |
| ---- | ---- |
| OS | LTS のサポート終了前に、新しい LTS のイメージでインスタンスを再作成し、コードから再構築する（インプレースのアップグレードは行わない） |
| Kubernetes | サポート対象のマイナーバージョンを維持するよう、計画的に引き上げる |
| アドオン | 自動更新で追従する。メジャーバージョンは計画的に引き上げる。開発が終了した場合は代替へ移行する |
| MySQL | OS のサポート範囲に従う。OS の移行に合わせて移行する |

インスタンスを再作成する場合のデータの引き継ぎは
[10章 バックアップ・リストア設計](../10.backup/10章_基本設計書_バックアップ・リストア設計.md) に従う。

## 12.7. アドオンと OCI CLI の自動更新

稼働中の版はクラスターとサーバ上の状態を正とし、サーバ上の定期実行で更新する。
更新の処理は本リポジトリで管理し、Ansible が CD で配置する。

| 項目 | 方針 |
| ---- | ---- |
| 実行時刻 | 毎日 04:30 |
| 版の選び方 | 配布元の正式リリース（先行版を除く）のうち、コードで指定したメジャーバージョン内の版 |
| 更新の単位 | マイナーバージョンは 1 回の実行で 1 つずつ上げ、そのマイナーバージョンの最新パッチを適用する |
| 公開後の待機 | 設けない |
| 中止条件 | ノードが Ready でない、または Kubernetes の更新失敗の記録がある場合は更新しない |
| 成功の確認 | 対象の Deployment・DaemonSet の入れ替えが完了すること |
| 失敗時 | 通知し、失敗の記録がある間はその対象を更新しない。他の対象の更新は続ける。自動の切り戻しは行わない |
| CD の役割 | 未導入の場合は指定範囲内の最新版を導入する。導入済みの場合は稼働中の版の構成を再適用し、版を変えない |
| 互換性 | Kubernetes との対応関係は自動で判定しない。成功の確認と通知で異常を検知する |

## 12.8. 手動で更新する版の検知

手動で更新する版は、Renovate が毎日確認し、更新の Pull Request を作成して知らせる。
自動マージは行わない。内容を確認してマージし、適用する。

| 対象 | 検知する更新 |
| ---- | ------------ |
| Kubernetes | 新しいマイナーバージョン |
| アドオン、OCI CLI | 新しいメジャーバージョン |
| CI の実行ツール、Terraform 本体と Provider、GitHub Actions | 新しいメジャーバージョン |
