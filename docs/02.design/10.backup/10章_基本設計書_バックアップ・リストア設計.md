## 10.1. 設計方針

- **構成はコードを正とする**: サーバの状態を取得して戻すのではなく、
  リポジトリのコードから再構築することを標準のリストア手段とする
- **クラウドの自動バックアップを使用しない**: ブートボリュームのバックアップは
  Always Free 枠を超える保存領域を要するため取得しない
- **データは論理バックアップで扱う**: 再構築で復元できないデータベースのデータは、
  ダンプの出力と取り込みで移送・復元する
- **共有データベースは基盤が一括で取得する**: データベースはホスト上の単一インスタンスを
  全サービスで共有するため、基盤が全データベースのダンプを定期的に取得する。
  各サービスはバックアップを個別に構成しない

## 10.2. バックアップ対象と方式

| 対象 | 方式 | 取得契機 |
| ---- | ---- | -------- |
| インフラ構成 | リポジトリのコード（Git） | 変更時 |
| OS・ミドルウェア構成 | リポジトリのコード（Git） | 変更時 |
| Terraform の state | Terraform Cloud の Workspace が保持する | 適用時（自動） |
| シークレット | OCI Vault が保持する | 作成・更新時（自動） |
| データベースのデータ | 論理バックアップ（全データベースのダンプ）を OCI Object Storage へ保管する | 日次（自動） |
| ブートボリューム | 取得しない | — |
| 各サービスのマニフェスト | 各アプリケーションのリポジトリ（本リポジトリのスコープ外） | — |

### 10.2.1. データベースのバックアップ方式

- **対象**: ホスト上の全データベース。データベースを追加した場合は、設定の追加なしに対象となる
- **取得方式**: データベース単位でダンプを出力し、圧縮して保管する
- **保管先**: OCI Object Storage。インスタンスの外に置き、Always Free 枠内に収まる範囲で保管する
- **認証**: インスタンスプリンシパルによる。長期の認証キーを発行・保管しない
- **世代**: 日次と月次の 2 系統で保管し、期間を過ぎたものは自動で削除する
- **権限**: ダンプ専用の読み取り専用ユーザーで取得する（[MySQL詳細設計書](../../03.detailed-design/MySQL詳細設計書.md)）
- **失敗時**: 失敗を通知する（[9章 監視・ログ設計](../09.monitoring/9章_基本設計書_監視・ログ設計.md)）
- **リストア検証**: 四半期に 1 回を目安に、取得済みのダンプを別名のデータベースへ取り込み、
  復元できることを確認する。実施は GitHub Issue で管理する

## 10.3. リストア方式

```mermaid
graph LR
    A["リポジトリのコード"] --> B["Terraform でインフラを再構築"]
    B --> C["Ansible で OS・ミドルウェアを再構成"]
    C --> D["各サービスのマニフェストを再適用"]
    D --> E["ダンプからデータを取り込み"]
```

| 対象 | リストア手段 |
| ---- | ------------ |
| インフラ構成 | Terraform を適用して再作成する |
| OS・ミドルウェア構成 | Ansible を適用して再構成する |
| シークレット | OCI Vault から取得する。Vault ごと再作成した場合は値を再登録する |
| データベースのデータ | Object Storage の最新のダンプを取り込む |

再構築の位置付けは
[5章 耐障害性](../05.availability/5章_基本設計書_耐障害性.md) を参照する。

## 10.4. 復元できない範囲

以下は構成上復元できない。許容したうえで運用する。

| 対象 | 状態 |
| ---- | ---- |
| 最後のダンプ取得以降のデータベースの更新 | 失われる |
| サーバ上で手作業により加えた、コード化されていない変更 | 失われる |
| インスタンスのパブリック IP | 再作成により変わる（DNS レコードの更新で対応する） |

目標復旧時点（RPO）は 1 日（日次ダンプの間隔）とする。
