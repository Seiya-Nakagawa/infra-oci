## 12.1. 設計方針

- **セキュリティ更新は自動、機能更新は手動**: 脆弱性への追従は自動化し、
  動作に影響しうるバージョン更新は人の判断で行う
- **勝手に上がらない状態を作る**: クラスターの構成に影響するミドルウェアはバージョンを固定し、
  意図しないアップグレードを防ぐ
- **再起動を自動化しない**: 単一インスタンス構成のため、
  再起動は全サービスの停止を伴う。自動再起動は行わず、実施タイミングを人が決める
- **更新はコードに反映してから適用する**: バージョンを変更する場合は、
  先にコードの指定を変更し、適用によって反映する。適用の単位・手順は
  [11章 リリース方式](../11.release/11章_基本設計書_リリース方式.md) に従う

## 12.2. 対象ごとの更新方式

| 対象 | バージョンの決め方 | 更新方式 | 脆弱性の検知 |
| ---- | ------------------ | -------- | ------------ |
| OS（Ubuntu） | LTS を採用し、リリース内で維持する | セキュリティ更新は自動適用。ディストリビューションのアップグレードは行わない | セキュリティ更新の自動適用で追従する。OpenSSH・OpenSSL は cve-notifier でも通知する |
| Kubernetes | バージョンを固定する。マイナーバージョンは 1 つずつ上げる | コードの指定を変更し、1 段階ごとに PR・CD で適用する（[12.4](#124-kubernetes-のバージョン管理)） | cve-notifier の CVE 通知。サポート終了前に追従する |
| コンテナランタイム | OS の提供版に追従する | OS のパッケージ更新に従う | セキュリティ更新の自動適用で追従し、cve-notifier でも通知する |
| ingress-nginx / cert-manager / External Secrets Operator / Flannel | バージョンを固定する。公式の対応表で、クラスターのバージョンに対応する版を選ぶ | コードの指定を変更して手動で適用する。クラスターに対応する版が未リリースの場合は更新を保留し、別 Issue で追従する | cve-notifier の CVE 通知 |
| MySQL | OS の提供版に追従する | OS のパッケージ更新に従う | セキュリティ更新の自動適用で追従し、cve-notifier でも通知する |
| Terraform Provider | メジャーバージョンを固定する | マイナーバージョンの更新のみ許容する | 対象外（CI・作業端末でのみ動作し、サーバでは稼働しない） |

cve-notifier による CVE 監視の方針と、監視対象の更新ルールは
[6章 6.6節](../06.security/6章_基本設計書_セキュリティ設計.md#66-os-堅牢化脆弱性対策) で扱う。

## 12.3. OS パッチ適用

| 項目 | 方針 |
| ---- | ---- |
| セキュリティ更新 | 自動適用の仕組みを有効化し、常時追従する |
| 自動再起動 | 無効化する。カーネル更新等で再起動が必要な場合は、任意のタイミングで手動実行する |
| パッケージの固定 | クラスターの構成に影響するパッケージは固定し、自動更新の対象から外す |

設定値は [OS詳細設計書](../../03.detailed-design/OS詳細設計書.md) で扱う。

## 12.4. Kubernetes のバージョン管理

- クラスターのコンポーネントはパッケージのバージョンを固定し、意図しない更新を防ぐ
- バージョンを上げる場合は、コードの指定を変更してから適用する
- シングルノード構成のため、更新中はサービスが停止する。
  無停止での更新は行わない
- アドオン（Ingress Controller・証明書管理・シークレット同期）は、
  クラスターのバージョンとの対応関係を確認したうえで更新する

### 12.4.1. 更新の適用方式

`k8s_version`（マイナーバージョン）の変更だけでは APT リポジトリが切り替わるのみで、
パッケージは固定（`hold`）されているため、クラスターは更新されない。
そのため、Ansible の `kubernetes` ロールに、クラスターを指定のマイナーバージョンへ
更新する処理を設ける。

| 項目 | 方針 |
| ---- | ---- |
| 起動条件 | 稼働中のクラスターのバージョンが `k8s_version` より低い場合のみ実行する。一致していれば何もしない（冪等） |
| 更新の単位 | kubeadm の制約により、マイナーバージョンは 1 つずつしか上げられない。差が 2 以上ある場合は更新せずに失敗させる |
| パッチバージョン | 指定のマイナーバージョンの最新パッチ（`<k8s_version>.*`）を APT から取得して適用する |
| 実行環境 | 本番は CI/CD（main マージ）のみ。`--check` では更新処理を実行せず、実適用でのみ検証される |

更新処理の流れは次のとおり。

1. APT リポジトリと署名鍵を `k8s_version` に切り替える（鍵は版ごとに取得し直す）
2. `kubeadm` の固定を外し、対象バージョンへ更新する
3. `kubeadm upgrade plan` で更新可能であることを確認する
4. `kubeadm upgrade apply` でコントロールプレーンを更新する
5. ノードを drain し、`kubelet`・`kubectl` を更新して `kubelet` を再起動し、uncordon する
6. 3 パッケージを再度固定し、API Server が正常（`/readyz`）になるまで待機する

### 12.4.2. 段階的な更新の運用

シングルノードのため更新中は全サービスが停止し、ダウングレードもできない。
そのため、複数のマイナーバージョンを一度に上げず、**1 段階ごとに PR・CD・動作確認を行う**。

| 項目 | 方針 |
| ---- | ---- |
| 進め方 | `k8s_version` を 1 つ上げる PR を作成し、CD の完了と動作確認を終えてから次の段階へ進む |
| 事前確認 | 更新前に、使用中の非推奨 API の有無と、アドオンの対応バージョンを確認する。直前の DB バックアップが成功していることも確認する |
| 動作確認 | ノードが Ready、全 Pod が Running、各サービスの HTTPS 疎通、Portfolio の死活監視が正常であることを確認する |
| 失敗時 | 次の段階へ進まず原因を調査する。`kubeadm upgrade apply` は更新前の etcd とマニフェストをバックアップするため、復旧の起点とする |
| アドオン | 更新後の Kubernetes が対応するバージョンへ、同じ段階の PR で更新する。ingress-nginx はアーカイブ済みで移行を別 Issue で扱うため、本方式の対象外とし、各段階で動作のみ確認する |

## 12.5. 証明書のライフサイクル

| 項目 | 方針 |
| ---- | ---- |
| 発行 | cert-manager が Let's Encrypt から自動取得する |
| 更新 | 期限前に自動更新する。手動での更新作業は行わない |
| 失効時の影響 | HTTPS での接続が不可となるため、更新の失敗はサービス影響として扱う |

## 12.6. EOL への対応

| 対象 | 対応 |
| ---- | ---- |
| OS | LTS のサポート終了前に、新しい LTS のイメージでインスタンスを再作成し、コードから再構築する（インプレースのアップグレードは行わない） |
| Kubernetes・アドオン | サポート対象のバージョンを維持するよう、計画的にバージョンを引き上げる |
| MySQL | OS のサポート範囲に従う。OS の移行に合わせて移行する |

インスタンスを再作成する場合のデータの引き継ぎは
[10章 バックアップ・リストア設計](../10.backup/10章_基本設計書_バックアップ・リストア設計.md) に従う。
