## 9.1. 設計方針

- **標準機能の範囲で行う**: 監視基盤（メトリクス収集・可視化製品）は導入せず、
  クラウド側の標準機能と OS 標準の仕組みで状態を把握する。
  追加のコンポーネントはリソースを消費し、単一インスタンス構成では
  監視系自体が停止すると機能しないため
- **常時監視を前提としない**: 個人開発基盤であり、障害の即時検知を要件としない。
  異常はサービスの挙動から把握し、必要なときにログをさかのぼって調査する
- **ログは 1 箇所に集約する**: 調査の起点を分散させないため、
  OS 上のログは journald に集約し、テキストログを出力するミドルウェアのみ世代管理する
- **ディスクを圧迫させない**: ログは保存容量に上限を設け、無制限に蓄積させない

## 9.2. 監視方式

| 対象 | 方式 | 目的 |
| ---- | ---- | ---- |
| インスタンスの稼働・リソース | Oracle Cloud Agent の監視プラグインで OCI 側のメトリクスを取得する | CPU・メモリ・ディスクの使用状況の把握 |
| Kubernetes のノード・Pod | クラスターのリソース使用状況を取得するアドオンを導入する | Pod の異常終了・リソース逼迫の確認 |
| データベース | スロークエリの記録を有効化する | 性能劣化の原因調査 |
| 公開サービスの死活 | 外形監視は行わない | — |

監視のしきい値・自動アクションは定義しない。取得したメトリクスは調査時に参照する。

## 9.3. ログ管理方式

| ログ種別 | 出力先 | 保持方針 |
| -------- | ------ | -------- |
| OS・systemd 管理下のサービス | journald | 保存容量の上限を設定し、超過分は古いものから破棄する |
| テキストファイルへ出力するミドルウェア | 各ミドルウェアのログディレクトリ | ログローテーションで世代管理し、圧縮して保持する |
| コンテナの標準出力 | コンテナランタイム経由でノード上に出力 | ランタイム側のローテーション設定に従う |
| 作業証跡（人・AI が実行したコマンドと出力） | 作業端末のローカル | リポジトリの管理対象外とする |

- ログ集約基盤（外部への転送・長期保管）は構成しない
- 保持期間・世代数などの設定値は
  [OS詳細設計書](../../03.detailed-design/OS詳細設計書.md)・
  [MySQL詳細設計書](../../03.detailed-design/MySQL詳細設計書.md) で扱う

## 9.4. 通知方式

自動通知は、データベースのバックアップ失敗に限り行う。
OCI Notifications のトピックを通じてメールで通知する。

上記以外の異常は、サービスの利用時、または作業時の状態確認で把握する。

状態確認は SSH 経由で行い、確認したコマンドと出力は証跡として記録する
（[8章 基盤制御](../08.platform-control/8章_基本設計書_基盤制御.md)）。
