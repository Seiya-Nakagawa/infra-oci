## 4.1. 設計方針

- **無償枠の上限まで確保する**: Always Free 枠で割り当て可能な最大のリソースを確保し、
  サービス追加のたびにサイジングを見直さなくてよい状態を作る
- **スケールアウトしない**: インスタンスの追加による水平スケールは行わない。
  リソース不足はサービスの整理、または Pod への割り当て見直しで対応する
- **性能要件は個別サービスで持つ**: 本基盤は応答時間・処理件数の目標値を定めない。
  個別の性能要件は各サービス側の設計で扱う

## 4.2. コンピュートリソース設計

| 項目 | 設計 | 選定理由 |
| ---- | ---- | -------- |
| シェイプ | `VM.Standard.A1.Flex`（ARM64） | Always Free 枠で唯一まとまったリソースを確保できるシェイプであるため |
| OCPU | 4 | Always Free 枠の上限 |
| メモリ | 24 GB | Always Free 枠の上限 |

ARM64 アーキテクチャを前提とするため、導入するミドルウェア・コンテナイメージは
ARM64 に対応したものを選定する（[1章 システム構成](../01.system-architecture/1章_基本設計書_システム構成.md)）。

## 4.3. ストレージ設計

| 項目 | 設計 |
| ---- | ---- |
| ブートボリューム | 200 GB（Always Free 枠の上限）。OS・コンテナイメージ・データベースの実体をすべて格納する |
| ブロックボリュームの追加 | 行わない。用途ごとのボリューム分割はせず、単一ボリュームで運用する |
| スワップ | OS 側で設定する（[OS詳細設計書](../../03.detailed-design/OS詳細設計書.md)） |

ディスク使用量は、コンテナイメージの蓄積とデータベースの増加が主な要因となる。
使用量の把握は [9章 監視・ログ設計](../09.monitoring/9章_基本設計書_監視・ログ設計.md) で扱う。

## 4.4. リソース配分の考え方

単一インスタンス上に Kubernetes とデータベースが同居するため、
いずれかがリソースを占有しないよう以下の方針で配分する。

| 対象 | 方針 |
| ---- | ---- |
| MySQL | バッファプールをインスタンスメモリの一部に固定し、上限を超えて拡張しない |
| Kubernetes の各 Pod | サービス側のマニフェストでリソース要求・上限を指定する（本リポジトリのスコープ外） |
| OS・システム領域 | 上記の割り当て後に残る領域を確保し、すべてをワークロードへ割り当てない |

## 4.5. 拡張方式

| 状況 | 対応 |
| ---- | ---- |
| 特定サービスの負荷増 | Pod のリソース割り当てとレプリカ数をサービス側で調整する |
| インスタンス全体のリソース不足 | シェイプの OCPU・メモリを引き上げる（Always Free 枠を超える場合は課金が発生するため、実施可否を都度判断する） |
| ストレージ不足 | 不要なコンテナイメージ・ログの整理を先に行い、解消しない場合にボリューム拡張を検討する |

いずれの拡張もインスタンスの追加は伴わない。
リソースを変更する場合は Terraform のコードを変更して適用し、
サーバ上で直接変更しない（[8章 基盤制御](../08.platform-control/8章_基本設計書_基盤制御.md)）。
