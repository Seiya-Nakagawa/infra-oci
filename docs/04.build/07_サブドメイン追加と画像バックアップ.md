## 1. 概要

Issue #151 の対応。Portfolio の商用化（SkillSheet）に伴い、次を行う。

- サブドメイン `skillsheet.technohonesty.com` を共有 Ingress に追加し、`portfolio-web` へルート（`/`）で転送する。
  既存の `technohonesty.com/portfolio` は旧 URL のリダイレクト用に残す
- TLS 証明書（`technohonesty-com-tls`）の対象に、サブドメインを加える
- アップロード画像の保存ディレクトリ（`/var/lib/portfolio/media`）を日次バックアップの対象に加える

設計は [ホスト名・パス割り当て台帳](../02.design/99.appendix/ホスト名・パス割り当て台帳.md) と
[10章 バックアップ・リストア設計](../02.design/10.backup/10章_基本設計書_バックアップ・リストア設計.md) を参照する。

## 3. 手順

### 3.1. ワイルドカードの DNS レコードを登録する

お名前.com の DNS 設定で、ホスト名 `*` の A レコードを 1 件登録する
（値は `technohonesty.com` の A レコードと同じ、インスタンスのパブリック IP）。

- 以後のサブドメインの追加では、DNS の登録は不要になる（既に登録済みの場合は本手順を省略する）
- 証明書の発行（HTTP-01）に名前解決が必要なため、**マージ（実適用）より前に**登録する
- 未登録のまま適用すると、証明書の再発行が失敗する。既存の証明書は発行に成功するまで使われ続けるため、
  既存ホストの通信には影響しない
- 個別に登録済みのレコード（MX・TXT 等）はワイルドカードより優先されるため、影響を受けない

### 3.2. Ansible の変更内容を確認する

PR 上のドライラン結果で、次のタスクに変更が出ることを確認する。

- `kubernetes` ロール: 共有 Ingress・Certificate のマニフェスト
- `backup` ロール: `/etc/mysql-backup.env` と `mysql-backup.sh`

### 3.3. 適用後に動作を確認する

マージ後の CD 完了後、インスタンスへ SSH 接続して確認する（[02 SSH 接続手順](02_SSH接続手順.md)）。

```bash
kubectl get certificate -n app-prod technohonesty-com-tls
```

```bash
kubectl get ingress -n app-prod shared-ingress
```

```bash
sudo systemctl start mysql-backup.service
```

```bash
sudo journalctl -u mysql-backup.service --no-pager -n 20
```

- Certificate が `READY=True` で、Ingress の HOSTS に両ホストが表示されること
- ジャーナルに `バックアップ完了: media-portfolio` が出力されること
  （ディレクトリが未作成の場合は「バックアップ対象外（ディレクトリなし）」と出力される。
  Portfolio アプリのデプロイ後に再確認する）
- Object Storage の `daily/{日付}/media-portfolio.tar.gz` が保管されていること
