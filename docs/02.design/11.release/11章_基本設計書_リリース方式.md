## 11.1. 設計方針

- **リリース単位を管理主体で分ける**: 共通基盤と、その上で動く各サービスを
  互いに独立してリリースできる状態を保つ
- **適用経路を増やさない**: Kubernetes 上のリソースであっても、基盤が管理するものは
  クラスター本体と同じ構成管理層から適用し、基盤の操作経路を一本化する
- **共有リソースは基盤側が所有する**: 複数のサービスが依存するリソースを個別のサービスに
  所有させない。いずれかのサービスを削除しても他のサービスが影響を受けない状態を保つ
- **切り戻しは再適用で行う**: 稼働中の状態を直接操作して戻すのではなく、
  以前のコードを適用し直すことで戻す

## 11.2. リリース対象と管理主体

| リリース対象 | 管理主体 | 適用の担い手 |
| ------------ | -------- | ------------ |
| ネットワーク、Compute インスタンス、シークレットの保管庫、IAM | 本リポジトリ（インフラ層） | Terraform |
| OS 設定、Kubernetes クラスター本体、データベース | 本リポジトリ（構成管理層） | Ansible |
| クラスター共通アドオン（Ingress Controller、証明書管理、シークレット同期） | 本リポジトリ（構成管理層） | Ansible |
| クラスター共通の設定リソース（証明書の発行元、シークレットの参照元） | 本リポジトリ（構成管理層） | Ansible |
| 各サービスのワークロードと公開設定 | 各サービスのリポジトリ | 各サービスのリリース手順 |

<mark>複数サービスが共有するドメインの証明書リソースの所有者は未確定（[Issue #114](https://github.com/Seiya-Nakagawa/infra-oci/issues/114)）</mark>

各層の実行方式は [8章 基盤制御](../08.platform-control/8章_基本設計書_基盤制御.md) で扱う。

## 11.3. 基盤のリリース単位

- インフラ層と構成管理層は、互いに独立して適用できる単位とする。
  インスタンスの再作成を伴わない構成変更のために、インフラ層を適用し直さない
- 構成管理層は役割単位で部分適用できる単位とし、変更した範囲のみを適用できる状態を保つ
- 適用は常に影響範囲の事前確認を伴う。確認の手順は
  [8章 基盤制御](../08.platform-control/8章_基本設計書_基盤制御.md) に従う

## 11.4. Kubernetes リソースのリリース

| 区分 | 管理主体 | 方針 |
| ---- | -------- | ---- |
| クラスター共通のリソース | 本リポジトリ | 構成管理層から適用する。クラスター構築と同一の経路に揃え、適用手段を分散させない |
| 各サービスのリソース | 各サービスのリポジトリ | 本リポジトリはサービスのマニフェストを保持しない |

サービス側のリソースが基盤へ依存する要素は、基盤側が提供し、サービス側は参照のみを行う。

| 依存する要素 | 提供元 |
| ------------ | ------ |
| Ingress の受け口（Ingress Controller と IngressClass） | 基盤 |
| 証明書の発行元 | 基盤 |
| 共有シークレットの参照元 | 基盤 |

## 11.5. 切り戻し

| 対象 | 切り戻し方法 |
| ---- | ------------ |
| インフラ層 | 以前のコードを適用し直す。状態管理ファイルを直接編集しない |
| 構成管理層 | 以前のコードを適用し直す |
| Kubernetes 上のリソース | 以前のマニフェストを再適用する |
| データ | [10章 バックアップ・リストア設計](../10.backup/10章_基本設計書_バックアップ・リストア設計.md) に従う |

単一インスタンス構成のため、切り戻しの最中はサービスが停止しうる。
無停止での切り戻しは行わない（[5章 耐障害性](../05.availability/5章_基本設計書_耐障害性.md)）。
